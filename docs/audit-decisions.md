## Generator mechanisms & builtins (full history)

- **Business-user workflow fixes** (2026-10-02, from 7 workflow tests, see `docs/business-user-playbook.md`): rolling catalog history (`CATALOG_HISTORY_KEEP`=12) + `compare_versions.py`; `customer_config.py` (audited set/create/exclude/include with old/new values; web PATCH records old/new too); per-customer exclusions `config/exclusions/<slug>.csv` (`prepare_rows(customer, template, slug)`; `excluded_skus_lookup` may be a list); cross-period check from both sides.
- **Known gaps copied into the snapshot** (2026-10-02, user decision): `build_real_cell_snapshot.py --known-gaps <report>` compares each real file with the current catalog and copies every differing cell (value or type) whose SKU is a coverage gap (the 105 SKUs absent from `cst_data_2.csv`) or an accepted residual: 30,604 cells, 180 columns in 73 templates wrapped in `real_cell_snapshot()`. Result: 236/236 customers `match`; `fidelity_accepted.json` emptied (mechanism kept). Note `fidelity_scoreboard.cst2_skus()` returns the *gap* SKUs (absent from cst_data_2), despite its name. - **Multi-sheet workbooks** (added 2026-10-01/02 for the Dutch templates `erasmus-mc-contract-line`, `radboud-umc-price-compare`, `sanquin-prijslijst`, `wageningen-catalogus`): `extra_sheets` entries may now be `{name, rows}` (static text copied cell-for-cell from the real file) as well as a bare name (empty tab); new template key `leading_sheets` (same format) places tabs *before* the data sheet, and `write_xlsx()` sets `wb.active` back to the data sheet so the row-count check and openpyxl readers still see it. `csv_format.header_row` is honored for xlsx too. Known limit: JSON can't carry Excel time values, so wageningen's two `Log` time cells are `HH:MM:SS` text.
- **Scoreboard compares the template's `sheet_name`** (2026-10-02): `compare_catalog.compare(..., sheet=)` reads that tab when both workbooks have it, instead of the first sheet carrying the SKU header. Found on sanquin, whose explanation sheet also carries the SKU header and had masked ~130k wrong data-sheet cells as "0 unexplained".
- **`generate_catalog.py all` continues past a failing customer** (2026-10-02): an exception (incl. `SystemExit` from an expression error) is printed as `ERROR`, audited `failed`, and skipped; the run exits 1. Found when a refresh died mid-run on a builtin registered after it started. The web UI regenerate job catches `SystemExit` too.

- **Fidelity tooling** (added 2026-09-25): `scripts/compare_catalog.py` compares one generated catalog with its real file across the full population: header order, row population by SKU, value and cell type (xlsx read with `data_only=False`), and CSV framing (line-ending style, BOM, trailer). - **Numeric-vs-text price cells** (found 2026-09-25 auditing `labviva-ucop-network`): a price expression returning a bare `round(x, 2)` float writes an actual number cell to `.xlsx` (e.g. `348.6`), but the real LabViva UCOP source files store every price column as literal 2-decimal text (`'348.60'`) — a genuinely different cell type, not just a display quirk, and distinct from the float-rounding-half-cent bug (the underlying value was already correct here; only its Python type/formatting was wrong). Worth checking cell type (not just value) against the real file for any `.xlsx` template's price columns going forward, not just its numeric correctness.

- **`_row_count_in_file()`/`check_row_count_regression()` now take the template's `delimiter`** (added 2026-09-24, found while rebuilding `google-merchant-center`): the row-count-regression warning always re-parsed a customer's previously-generated `.csv` with a hardcoded comma delimiter, regardless of what delimiter that file actually used — for any semicolon-delimited `.csv` template this silently produced a nonsense row count (inflated by unquoted embedded newlines inside multi-line text cells being read as extra rows), which then fired a spurious large "row count dropped/increased" warning on every subsequent generate. A real, generic bug, not specific to one template — it went unnoticed until now only because `universitat-heidelberg`/`unimarket` (the pre-existing semicolon-delimited real source files) never had a semicolon-delimited *generated* output to compare against until `google-merchant-center` did. Now reads `template.get("delimiter", ",")` and passes it through; every comma-delimited template (the default) is unaffected.
- **`price_for_rounded()` expression builtin** (added 2026-09-24 for `sap-gdsn-price-de`): computes a discounted price in `Decimal` arithmetic (round-half-even) and returns a 2-decimal string, instead of `round(float(x) * (1 - discount/100), 2)` or equivalent. The latter is a real bug, not just a style preference — it hits binary floating-point representation error on exact-half-cent results (e.g. `191.00 × 82.5% = 157.575` mathematically, but naive float rounding silently picks the wrong cent). Confirmed present in `sap-gdsn-price-de` (fixed). **Swept across every template 2026-09-24**: of 133 price expressions using the naive `round(... discount ...)` pattern across ~90 templates, only 5 customer/discount combinations actually hit a live exact-half-cent collision against today's master data (the other 260+ are latent-only — the bug is real but dormant at their current discount value, so left as-is rather than churned unnecessarily) — `universitat-heidelberg`/`-future`, `eu-imba`/`-future`, `uni-nottingham`/`-future`, `fskk-staffelpreis`/`-future`, and all 22 institution columns of `one-advanced-network` (`one-advanced`/`-future`). All 5 verified against their real files to use `ROUND_HALF_UP`, not `ROUND_HALF_EVEN` — switched to `price_for_rounded_half_up()`. `fskk-staffelpreis` has a residual 622/24,765 (2.5%) mismatch even under `ROUND_HALF_UP`, on exact-half-cent ties where the real file itself is internally inconsistent about which way it rounds — same class of unexplained residual as Helmholtz's, documented rather than chased further. Auditing `one-advanced-network`'s Current file also surfaced an unrelated real bug found along the way: `config/customers/one-advanced.json` had 8 institutions' `discount_percentage` values cyclically shifted (each held the value that belonged to a different institution) — corrected against the real file (0 mismatches across all 22 institutions, 24,764 rows each) — and `one-advanced-future.json` had never modeled the real Future file's full reversion to 0% discount for any of its 22 institutions (same "Future reverts to list price" pattern as `de-helf-future`/`eu-imba-future`/etc.) — now corrected. **`price_for_rounded_half_up()`** (added 2026-09-24 for `de-boehringer-austria`) is the same idea with `ROUND_HALF_UP` instead of `ROUND_HALF_EVEN` — a separate function, not a parameter on `price_for_rounded()`, so `sap-gdsn-price-de`'s already-verified call sites can't change behavior. Boehringer's real Unit Price disagreed with `price_for_rounded()` on every exact-half-cent case (e.g. Forschungsinstitut's 7.5% discount on `505.00 EUR`: `505.00 × 92.5% = 467.125`; the real file has `467.13`, which is round-half-**up**, not round-half-even's `467.12`) — the correct rounding mode is genuinely per-template, not a single universal fix, so check which one a new template needs rather than assuming `price_for_rounded()`'s mode applies. Reused again for `univ-tennessee`'s 2026-09-25 audit, but for a different reason than every case above: both its customers are 0%-discount, so the half-cent rounding-mode bug can never actually fire there — the real bug was `round(x, 2)`'s bare-float serialization (`'415.0'`) versus the real file's fixed 2-decimal string (`'415.00'`), a plain formatting gap, not the binary-representation issue this builtin was built for. A reminder that `price_for_rounded()` is worth using purely for its string formatting even when a template's discount makes the rounding-mode question moot. `uni-hull`'s 2026-09-25 audit is the same class of reuse as `univ-tennessee`'s (both customers 0%-discount, so purely a `'614.0'`-vs-`'614.00'` string-formatting fix) — it also surfaced a residual (259/24,764 Current, 529/24,764 Future rows) where the real file's own `Price` column drops the trailing `.00` on a minority of rows. A same-day follow-up traced this to the raw `UK_CLP`/`UK_Future_CLP` strings in `incoming/cst_data_2.csv`, which are integer-formatted for exactly those SKUs and erased by `master/products.csv`'s 2dp reformat. `Price` now reads `master/cst_uk_clp.csv` via `lookup()`, falling back to `price_for_rounded(..., 0)`, which leaves 1 row per file (`5748P2`, absent from `cst_data_2.csv`). `University of Hull` never shows the quirk and is unchanged. Root cause of the recurring whole-number-vs-decimal price quirk (`'614'` vs `'614.00'`): the raw price strings in `incoming/cst_data_2.csv` (`UK_CLP`/`UK_Future_CLP`, `eu_list_price`/`eu_future_list_price`) are integer-formatted for a minority of SKUs, and `master/products.csv`'s import normalizes every price to 2dp. So an undiscounted list-price column should read the raw string via `lookup()` (`master/cst_uk_clp.csv` or `master/cst_dkfz_bmecat_fields.csv`) and fall back to `price_for_rounded*()` when it's blank. Only SKUs missing from `cst_data_2.csv` (e.g. `5748P2`) remain.
- **Column `"key"` field** (added 2026-09-24 for `sap-gdsn-price-de`): disambiguates a real source file's genuinely duplicate header name (e.g. two columns both literally named `PRICE_AMOUNT`, only the first ever populated) — `build_rows()` keys its internal row dict by `col.get("key", col["header"])` instead of the header text itself, and `write_xlsx()`/`write_csv()` take a matching `keys` list so the written file still shows the real (duplicate) header text. Defaults to the header when absent, so no pre-existing template is affected. Without this, `build_rows`'s dict-keyed row representation silently lets a later duplicate-named column's value clobber an earlier one — a real generator bug this fix closes, not merely a modeling nicety.
- **`overrides.excluded_skus_lookup`** (added 2026-09-24 for `coupa-marketplace-de`/`-uk`): names a lookup CSV (loaded via the same `load_lookup()`/cache as `lookup()` — any column layout, only SKU membership matters) whose SKUs are dropped from that customer's row population entirely, applied in `generate()` right after `load_master()` and before `build_rows()`. For a real customer file that's a genuine *subset* of another region/customer's SKU population, not a config error — e.g. `coupa-marketplace-de`/`-uk` real files exclude ~1,457/1,458 of US's 26,222 SKUs (mostly V2/V3/V4 multi-unit kit sizes, plus a handful of high-value cold-chain SKUs with no discoverable common rule). Absent by default, so no pre-existing template/customer is affected. `fisher-scientific-de`/`-uk` (added 2026-09-24) and `boehringer-forschungsinstitut-austria`/`boehringer-rcv-austria` (both price periods, added 2026-09-24) all reuse `coupa-marketplace-de`/`-uk`'s existing `master/coupa_marketplace_excluded_de.csv`/`_uk.csv` files directly rather than duplicating them — confirmed byte-identical exclusion sets (not just matching counts) each time, a shared quirk of the same underlying source feed spanning multiple, unrelated real customer contracts. `merck-kgaa`/`-future` and `uni-oxford`/`-future` (both added 2026-09-24) also exclude ~1,457/1,458 SKUs each in the same mostly-V2/V3/V4-kit-size shape, but via their own dedicated files (`master/merck_kgaa_excluded_de.csv`, and `uni-oxford` reuses `coupa-marketplace-uk`'s existing exclusion file directly, confirmed byte-identical) rather than assuming every occurrence of this pattern shares one file — check byte-identity before reusing, don't just match on count. `vertex-labviva-uk`/`-future` (added 2026-09-25) is a fourth, unrelated UK customer confirmed to reuse `coupa-marketplace-uk`'s exact same 1,458-SKU exclusion set byte-for-byte. `uni-hull`/`-future` and `uni-nottingham`/`-future` (both added 2026-09-25) are a fifth and sixth.
- **`clean_coupa_description()` expression builtin** (added 2026-09-24 for `coupa-marketplace`): region-aware HTML-entity/tag cleaning for a description field, taking `(text, region)`. Added because a single real template had **three different real per-region text-cleaning conventions** for the same source field (`us`: only replace bare/paired `®`/`™` markers, leave every other tag untouched; `de`: also strip all remaining tags to a single space each then collapse runs of whitespace; `uk`: normalize a pseudo-escaped tag form first, then strip all remaining tags with no space) — see `coupa-marketplace.json`'s own `description` and `docs/baseline-reconciliation.md` for the full byte-level reasoning. A reminder that "identical template, different customer" is never safe to assume — verify per real file (see [[verify_template_claims_against_full_population]]).
- **`clean_boehringer_description()` expression builtin** (added 2026-09-24 for `de-boehringer-austria`'s Item Description/Short Name): strips every HTML-ish tag (`<sup>`, `<sub>`, `<i>`, `<p>` and their closing forms, the bare self-closing `<R/>`, and even the pseudo-escaped `<lt/>`/`<gt/>` tokens a few SKUs use in place of real angle brackets) to a single space via one generic regex, collapses runs of 2+ spaces, trims the ends, and replaces any bare `®` with the literal text `00AE` (the same garbled-entity artifact as `sap-gdsn-price-de`'s `buggy` mode) while leaving `™` untouched — a real, confirmed asymmetry from that other template's handling of the same two symbols. Deliberately does NOT reassemble `<lt/>sup<gt/>`/`<lt/>/sup<gt/>` into real tags first the way `coupa-marketplace`'s `uk` mode does: a few Boehringer SKUs' real files genuinely show the leftover literal words `sup`/`/sup` where those pseudo-tags sat, and replicating that meant NOT normalizing them. Verified byte-for-byte across the full population of all 4 real files (both institutions, both price periods) except SKUs entirely missing from `incoming/cst_data_2.csv` (same class of residual as `ghx-gdsn-nl-hospital`/`sap-gdsn-price-de` above) — see `docs/baseline-reconciliation.md`.
- **`clean_gladstone_description()` expression builtin** (added 2026-09-24 for `distributor-staggered-gladstone`'s ShortDescription/LongDescription): strips only `<sup>`/`</sup>`, `<sub>`/`</sub>`, `<i>`/`</i>` tags (pseudo-escaped `<lt/>sup<gt/>`/`<lt/>/sup<gt/>` normalized to real tags first), with no entity substitution at all - a bare `®`/`™` or the bare self-closing `<R/>` tag passes through completely untouched, unlike every other cleaning builtin in this file. Original full text of the "Quality checks" section (the Cross-period consistency bullet is above):

#### Quality checks (in `generate_catalog.py`)
Blocking — a failed check stops the write and logs an `outcome: "failed"` audit entry with the specific errors; nothing partial gets written:
- **Config sanity** (`check_config_sanity`, runs before any row is built): a template's `sku_column` and every `price_columns` entry must actually be one of its declared columns
- **Master data integrity** (`check_master_data`, checked once per run against `master/products.csv` itself, independent of customer/template): no blank/duplicate `sku`; no blank `short_description`; `list_price_usd` numeric and > 0; `unspsc` is 8 digits when present; `cas_number` matches CAS format when present
- **Discount ranges**: `discount_percentage`, each `category_discounts` value, and each `institutions.*.discount_percentage` (SciQuest) in [0, 100]
- **Price validity window**: `price_valid_from` < `price_valid_until`
- **Output SKUs**: no blank or duplicate values in the template's `sku_column`
- **Price columns**: no negative/non-numeric values in declared `price_columns`
- **Price relationships** (`check_price_relationships`, where the columns exist): tiered prices (`Price 1/2/3`) must be non-increasing; `Discounted Price` ≤ `List Price`; the implied discount from list/discounted price must match one of the customer's configured discounts — catches a broken template expression, not just a bad value
- **Required fields** (`check_required_fields`): any column with "description" in its header can't be blank

Non-blocking warnings — surfaced in the CLI, the audit log, and the web UI, but don't stop the write:
- **Override coverage** (`check_override_coverage`): flags when a SKU-keyed override (e.g. Zageno's `overrides.regional_prices`) doesn't cover the full row population
- **Row-count regression** (`check_row_count_regression`): compares against that customer's last generated catalog and warns on a ≥10% swing — this is what surfaces the stale-catalog situation below at generation time
- **Category discount distribution** (`check_category_discount_distribution`): reports how many rows landed in each `category_discounts` bucket (e.g. a `kit`/`default` split), reconstructed from realized prices rather than duplicating the template's text heuristic

- `config/customers/{slug}.json` — one file per B2B customer/channel. Defines `template_ref`, `discount_percentage`, `price_valid_from`/`price_valid_until`, `file_type`, and `overrides`.
- `catalogs/{slug}/` — generated output, one folder per customer.
- `audit/{date}.jsonl` — append-only, one line per audited action (who/what/when/outcome), written on both success and failure. Two `action` values: `generate_catalog` (from the CLI or the web UI's Preview/Generate) and `update_customer_config` (from the web UI's config edits only — the CLI has no equivalent). A successful `generate_catalog` entry's `detail` is structured as `{"rows_written": N, "warnings": [...]}`; a failed one is `{"errors": [...], "warnings": [...]}`. Entries from before 2026-09-01 predate this and have a plain human-readable string `detail` instead — the web UI's status badge (see Web UI below) treats those as "no warnings known" rather than trying to parse them.
- `scripts/generate_catalog.py` — the generator, importable as a module (via `scripts/__init__.py`) so the web UI reuses its functions directly instead of duplicating logic. CLI usage: `python3 scripts/generate_catalog.py <customer-slug|all> [--requested-by X] [--request "..."] [--dry-run]`.
- `scripts/import_master_data.py` — maps a raw CST product data export (like `incoming/cst_data.csv`) onto `master/products.csv`'s schema and overwrites it. The export's column names don't match the master schema, and a couple are mislabeled relative to their actual content (`gbp` holds the USD list price when `CURRENCYCODE` is USD; `Image_URL_US` holds a product page link, not an image — `primary_image_url` is the real image). Usage: `python3 scripts/import_master_data.py <path.csv> [--requested-by X] [--dry-run]`. Logs an `import_master_data` audit entry (not `generate_catalog`). Run `generate_catalog.py <slug|all>` afterward to refresh customer catalogs against the new data.
- `webapp/backend/main.py` + `webapp/frontend/index.html` — the web UI (see Web UI below).
